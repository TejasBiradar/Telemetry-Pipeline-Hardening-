## 1. Business problem
*(Source: brief #31)*

Event telemetry goes bad **quietly**:
- a field changes unit
- a client version stops sending data
- a field becomes nullable, but later steps assume it is always there

Nothing fails loudly and dashboards keep showing numbers. The damage is found only when someone questions a number, **weeks later**.

## 2. Goal
Take a telemetry pipeline that the team did not write and:
1. understand what it really does
2. protect its current behaviour with tests
3. add checks that catch silent data damage early and say where it came from
4. prove the checks work, and prove the pipeline's output is unchanged

## 3. Who is affected
*(Source: brief #31)*

| Who | How they are affected today |
|---|---|
| People who rely on dashboards built from the pipeline | They see wrong numbers without knowing it |
| People who run or own the pipeline | They find problems late and can't easily tell where they started |

## 4. Scope

### In scope
*(Source: brief #31)*
1. Mapping the supplied pipeline with a code graph
2. Writing down what the pipeline actually guarantees
3. Characterisation tests written before any change
4. Quality checks that act as gates
5. Drift detection on numeric fields and on text payloads
6. Alerts with lineage back to the emitting source
7. Injecting degradations and reporting which checks catch them, and how quickly
8. Keeping changes inside a controlled blast radius
9. Proving the pipeline still produces equivalent output

### Out of scope
| Item | Source |
|---|---|
| Real customer data, PII, or any C5i/client data | Programme rule |
| Changing what the pipeline calculates (its business logic) | Brief: "prove the pipeline still produces equivalent output" |
| Fixing bugs in the supplied pipeline | Brief: characterise current behaviour; keep the change inside a controlled blast radius |

### Decided by the team
| Item | Decision | Date |
|---|---|---|
| Where the pipeline comes from | An **existing open-source pipeline**, so no team member knows its code beforehand | 2026-09-29 |
| Pipeline styles supported | **Python and SQL** pipelines, at minimum | 2026-09-29 |
| When the pipeline and checks run | **Event-driven, per batch on arrival**: each time a new batch/file is ingested, the pipeline and checks run on it (not per single event) | 2026-09-29 |
| AI inside the product | **Alert explainer** only: turns an alert into a plain-English summary. It explains; it never decides pass/fail | 2026-09-29 |

## 5. Functional requirements

Each requirement has **acceptance criteria**, i.e. the tests that show it is done. Where the criterion needs a number that nobody has given us, the number is **TBD**.

### FR-1: Receive and freeze the pipeline
The pipeline under test is stored unchanged and protected from edits.
- **AC-1.1** The pipeline code is stored in its own read-only folder.
- **AC-1.2** A fingerprint (checksum) of every file is recorded when it is received.
- **AC-1.3** An attempt by the coding agent to edit the pipeline is blocked, and this is demonstrated.
- **AC-1.4** The pipeline runs from the repository and produces its normal output.

### FR-2: Code graph
Map the pipeline's code: files, functions, fields, and how data flows to the outputs.
- **AC-2.1** The graph is generated by a command, not drawn by hand.
- **AC-2.2** For any field, the graph can list the outputs it affects and the fields it comes from.
- **AC-2.3** Every link in the graph points to the file and line it came from.
- **AC-2.4** The graph is checked against one real run of the pipeline, and the agreement is reported.

### FR-3: Reconstructed guarantees
Write down what the pipeline actually guarantees and assumes.
- **AC-3.1** A `GUARANTEES.md` lists each rule with its evidence (file and line).
- **AC-3.2** Every rule has been reviewed by a team member (marked confirmed or rejected).
- **AC-3.3** Where the coding agent was wrong about the code, this is recorded in the review log.
- **AC-3.4** If an answer key exists, the rules are scored against it. **TBD**, Q3

### FR-4: Characterisation tests
Pin the pipeline's current behaviour **before** any change.
- **AC-4.1** The tests exist and pass on the unchanged pipeline before any hook or check is added.
- **AC-4.2** The tests include unusual inputs (e.g. empty batch, missing values, duplicates).
- **AC-4.3** Behaviour that looks wrong is pinned as it is, and listed as a known issue.
- **AC-4.4** Test coverage is measured and reported. Coverage type and target: **TBD**, Q7 / Q16

### FR-5: Quality checks as gates
Checks run inside the pipeline and can stop a bad batch.
- **AC-5.1** Checks run at the boundaries between pipeline stages.
- **AC-5.2** Checks cover: schema/type, missing values, value ranges, units, and data volume.
- **AC-5.3** Checks run separately per emitting source (e.g. per client version).
- **AC-5.4** A failing batch can be stopped. Whether it is blocked or quarantined: **TBD**, Q11
- **AC-5.5** Checks can be switched off instantly, and the pipeline then behaves exactly as before.
- **AC-5.6** A crash inside a check does not crash the pipeline.

### FR-6: Numeric drift detection
Detect when numeric fields stop looking normal.
- **AC-6.1** "Normal" is learned from good historical data and stored.
- **AC-6.2** Sudden changes (e.g. a unit change) are detected.
- **AC-6.3** Gradual changes are detected.
- **AC-6.4** On clean data, the number of false alarms is reported.

### FR-7: Text payload drift detection
Detect when text fields stop looking normal.
- **AC-7.1** Changes in text structure and content are detected (e.g. new message patterns, changed format).
- **AC-7.2** On clean data, the number of false alarms is reported.
- **AC-7.3** What counts as a "text payload" (free text, JSON structure, or both): **TBD**, Q12

### FR-8: Alerting with lineage
Alerts say what broke, where it came from, and what it affects.
- **AC-8.1** Each alert names the field and the emitting source.
- **AC-8.2** Each alert lists the affected outputs, taken from the code graph.
- **AC-8.3** One problem produces one alert, not many.
- **AC-8.4** Lineage completeness is measured. Definition: **TBD**, Q9

### FR-12: Alert explainer (AI)
Each alert gets a short plain-English explanation generated by an LLM.
- **AC-12.1** The explanation uses only the alert's own facts (check results, source, lineage). Every claim can be traced to one of them.
- **AC-12.2** The explainer never changes an alert's status, severity or pass/fail result.
- **AC-12.3** If the LLM is unavailable or fails, the alert is still raised and shown, just without the explanation.
- **AC-12.4** Explanation accuracy is measured on a labelled set of alerts from injected degradations, where the true cause is known. The target: **TBD**, Q16
- **AC-12.5** No secrets or credentials are sent to the LLM; the API key is kept in the secrets manager (NFR-5).

### FR-9: Degradation injection and reporting
Break the data on purpose and measure the checks.
- **AC-9.1** The degradations include at least the three in the brief: unit change, a client version that stops sending, a new nullable field. The full list: **TBD**, Q5
- **AC-9.2** Clean runs (no degradation) are included, to measure false alarms.
- **AC-9.3** The report shows, per degradation: which checks caught it, and how quickly.
- **AC-9.4** Results are compared with a baseline. Which baseline: **TBD**, Q4
- **AC-9.5** Running the evaluation twice with the same settings gives the same numbers.
- **AC-9.6** Thresholds are not tuned on the data used for the final numbers.

### FR-10: Controlled blast radius
Changes to the pipeline are as small as possible and fully visible.
- **AC-10.1** Every change to the pipeline code is listed, with file, line and reviewer.
- **AC-10.2** An automatic check fails if the pipeline code changes outside the listed lines.
- **AC-10.3** How the blast radius is to be demonstrated to the panel: **TBD**, Q13

### FR-11: Output equivalence
With our changes in place, the pipeline produces the same output as before.
- **AC-11.1** On the same input, the output with checks switched on is compared with the original output.
- **AC-11.2** The comparison result is reported. "Equivalent" means exact or within a tolerance: **TBD**, Q8

## 8a. Selection criteria for the open-source pipeline
The pipeline is chosen using **only its description, README and licence**. Nobody reads its code before it is frozen (FR-1).

| # | Must have | Why |
|---|---|---|
| 1 | Written in Python and/or SQL | The styles we support |
| 2 | Processes event / telemetry-style data (events with source, version, numbers and text) | Brief #31 is about telemetry |
| 3 | Runs locally on data we generate (no paid cloud services) | Synthetic data only; runs from a clean clone |
| 4 | Licence allows copying and modifying (e.g. MIT, Apache-2.0, BSD) | Legal use |
| 5 | Small enough to understand in the time available, with more than one stage | Must be mappable, but not trivial |
| 6 | Has no complete test suite of its own | We write the characterisation tests |

## 11. Glossary
| Term | Meaning |
|---|---|
| Telemetry | Data that apps, devices or servers send automatically about themselves |
| Pipeline | The code that collects this data and turns it into numbers and dashboards |
| Code graph | A map of the pipeline's code: functions, fields, and how data flows between them |
| Characterisation test | A test that records what the code does today, even if that looks wrong |
| Gate | A check inside the pipeline that can stop bad data |
| Drift | Data slowly or suddenly stops looking like normal data |
| Lineage | The trail from a number back to where its data came from |
| Degradation / injection | Damaging data on purpose to test the checks |
| Blast radius | How much of the pipeline our change touches |
| Baseline | The "before" result we compare our results against |
